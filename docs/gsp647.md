# GSP647 - Configuring IAM Permissions with gcloud

Runbook untuk [`gsp647.sh`](../gsp647.sh). Status: **terverifikasi 100/100** (2026-08-07).

Lab pengenalan dengan **dua project dan dua akun user**. Dua fase: pekerjaan resource dari Cloud Shell, lalu pekerjaan lokal di VM `centos-clean`.

## Temuan utama: sebagian checkpoint dinilai dari dalam VM

Ini yang bikin lab ini beda dari lab lain di repo dan wajib dibaca sebelum jalan.

Empat dari dua belas checkpoint **tidak membaca Google Cloud API dari luar**, melainkan dijalankan dari dalam `centos-clean`:

- *Update the default zone* dan *Create a configuration for Username 2* membaca `~/.config/gcloud/` milik VM. Home Cloud Shell ada di luar project lab, jadi grader memang tidak bisa melihatnya. **Tidak butuh kredensial asli** — `gcloud config set` tidak memvalidasi apa pun ke API, jadi configuration `user2` cukup dibuat dengan `account` dan `project` terisi. `gcloud init --no-launch-browser` tidak diperlukan.
- Seluruh checkpoint IAM Project 2 butuh tiga hal di VM: gcloud berjalan sebagai **Username 1** (`gcloud auth login`), env var `PROJECTID2` dan `USERID2` ada di `~/.bashrc`, dan **`jq` terpasang**.

Petunjuknya ada di teks lab sendiri: ia menyuruh menulis `PROJECTID2`/`USERID2` ke `~/.bashrc` dan memasang `jq`, padahal `jq` tidak dipakai satu perintah pun yang ditampilkan. Itu perkakas grader.

Terbukti di lab: dengan semua binding, custom role, dan service account sudah benar di Project 2 (diverifikasi lewat `get-iam-policy`), keenam checkpoint IAM tetap 0 sampai VM disiapkan. Setelah `gcloud auth login` + bashrc + jq, semuanya langsung hijau.

## Jalankan

**Fase 1 — Cloud Shell, sebagai Username 1:**

```bash

bash gsp647.sh
```

Project kedua dan email Username 2 dideteksi sendiri, tinggal Enter dua kali.

**Fase 2 — SSH ke `centos-clean` dari Console:**

```bash
gcloud auth login          # Username 1, ikuti link + tempel kode
curl -sLO https://raw.githubusercontent.com/ravi-arnan/gsp_lab_solutions/main/gsp647.sh
bash gsp647.sh vm
```

`gcloud auth login` adalah **satu-satunya langkah yang butuh browser**. Akun aktif bawaan VM adalah compute service account, yang tidak bisa membaca IAM Project 2.

Baru setelah itu klik Check my progress; kedua belas checkpoint bisa diklik sekaligus.

## Detail yang gampang salah

- **`--condition=None` di setiap `add-iam-policy-binding`.** Tanpa itu gcloud bisa berhenti menanyakan condition saat policy sudah punya binding bersyarat, dan script menggantung.
- **`CLOUDSDK_ACTIVE_CONFIG_NAME=user2` per perintah**, bukan `configurations activate user2`. Kalau configuration aktif benar-benar dipindah ke `user2` (yang tidak punya kredensial), semua perintah setelahnya gagal.
- **Jangan set `compute/region` atau `compute/zone` pada configuration `user2`.** gcloud memvalidasinya lewat API dan menolak dengan `does not have any valid credentials`. Cukup `account` dan `project`, dan `project` butuh `-q` supaya peringatan "you do not appear to have access" tidak menunggu jawaban.
- **Jangan `configurations activate default` di akhir.** Di Cloud Shell configuration aktif bernama `cloudshell-NNNN`, bukan `default`, jadi itu memindahkan alih-alih mengembalikan.

## Troubleshooting

| Gejala | Sebab dan solusi |
|--------|------------------|
| Semua checkpoint IAM merah padahal binding terbukti ada | Fase `vm` belum dijalankan, atau dijalankan sebelum `gcloud auth login`. Ini penyebab paling umum di lab ini. |
| `Project kedua tidak terdeteksi` di fase vm | gcloud di VM masih memakai compute SA. Jalankan `gcloud auth login` dulu. |
| `Project kedua tidak terdeteksi` di fase cloud | Salin Project ID dari panel lab: `PROJECT2=... bash gsp647.sh`. |
| `Username 2 tidak terdeteksi` | Salin email dari panel lab: `USERID2=... bash gsp647.sh`. |
| `Quota exceeded` saat membuat instance | Tiga instance `e2-standard-2` plus `centos-clean`. |
| `PERMISSION_DENIED` di Project 2 | Fase cloud dijalankan sebagai Username 2. Jalankan sebagai Username 1. |
