# GSP364 - Monitor Environments with Google Cloud Managed Service for Prometheus: Challenge Lab

Runbook untuk [`gsp364.sh`](../gsp364.sh). Status: **terverifikasi 100/100** (2026-08-10), semua checkpoint hijau sekali jalan tanpa intervensi.

## Cara jalan

```bash
curl -sLO https://raw.githubusercontent.com/ravi-arnan/gsp_lab_solutions/main/gsp364.sh
bash gsp364.sh
```

Dua pertanyaan di awal (zone dan nama cluster), defaultnya `us-east1-d` dan `gmp-cluster`. Zone dikunci instruksi lab — tekan Enter saja kecuali panel lab menyebut yang lain. Semua task otomatis, tidak ada langkah Console. Lama ~10 menit, hampir semuanya menunggu GKE.

| Task | Otomatis | Cara |
|------|----------|------|
| 1 Cluster GKE | ya | `gcloud container clusters create --zone us-east1-d --enable-managed-prometheus` |
| 2 Managed collection | ya | `kubectl apply -f manifests/setup.yaml` + `manifests/operator.yaml` dari `GoogleCloudPlatform/prometheus-engine` |
| 3 Example app | ya | `examples/example-app.yaml` + PodMonitoring, di namespace `default` dan `gmp-test` |
| 4 Filter metrik | ya | OperatorConfig `collection.filter.matchOneOf` + unggah `op-config.yaml` ke bucket publik |

## Yang tidak disebut instruksi lab tapi diperlukan

### `--enable-managed-prometheus` tidak bisa ditambal belakangan dengan mudah

Kalau cluster terlanjur dibuat tanpa flag itu, checkpoint Task 1 merah. Script mencoba `clusters update --enable-managed-prometheus` saat menemukan cluster yang sudah ada, tapi cara paling bersih adalah menghapus cluster lalu membiarkan script membuatnya sendiri.

### PodMonitoring tidak ada di `example-app.yaml`

`examples/example-app.yaml` **hanya berisi Deployment** (dicek di v0.17.0). Tanpa PodMonitoring tidak ada yang men-scrape pod itu, jadi filter `{job="prom-example"}` di Task 4 tidak pernah mengenai metrik apa pun. Script menambahkan PodMonitoring `prom-example` sendiri — murah, dan membuat skenarionya benar-benar jalan kalau checkpoint ternyata memeriksa metrik di Cloud Monitoring, bukan sekadar keberadaan resource.

Webhook operator kadang belum siap sesaat setelah `operator.yaml` di-apply, jadi apply PodMonitoring diulang sampai 3 kali dengan jeda 20 detik.

### Namespace example-app tidak ditentukan

Instruksi lab tidak menyebut namespace dan walkthrough yang beredar terbagi antara `default` dan `gmp-test`. Script memasang di **keduanya**. Tidak ada ruginya: filter `job="prom-example"` mengenai dua-duanya, dan biayanya satu apply tambahan.

### Apply manifest di atas managed collection bawaan GKE

`--enable-managed-prometheus` sudah memasang operator versi GKE di `gmp-system`. Meng-apply `operator.yaml` self-managed di atasnya kadang ditolak di field immutable. Itu **tidak** menggagalkan checkpoint (resource-nya sudah ada), jadi script hanya mencetak peringatan dan lanjut, bukan berhenti.

### Bucket harus fine-grained ACL

Instruksi lab memakai `gsutil -m acl set -R -a public-read`, dan perintah itu **ditolak di bucket dengan uniform bucket-level access**. Script membuat bucket dengan `gsutil mb -b off` (fine-grained). Kalau `acl set` tetap gagal, ia jatuh ke `add-iam-policy-binding allUsers/objectViewer` yang bekerja di bucket UBLA.

## Task 4 dinilai dari file, bukan dari cluster

Yang dibaca grader adalah `gs://$PROJECT/op-config.yaml` lewat URL publik, bukan isi OperatorConfig di cluster. Script menulis file itu dulu lalu `kubectl apply -f` file yang sama, jadi keduanya dijamin identik. Di akhir script mencetak status HTTP dari `https://storage.googleapis.com/$PROJECT/op-config.yaml` — kalau bukan `HTTP 200`, checkpoint Task 4 akan merah walau clusternya benar.

## Versi manifest

Diambil dari release terbaru lewat GitHub API, fallback `v0.17.0`. `|| true` pada pipeline itu bukan hiasan: tanpa itu `grep` yang tidak menemukan apa-apa membuat `set -e` membunuh script sebelum baris fallback sempat jalan (ketahuan di dry-run harness).
