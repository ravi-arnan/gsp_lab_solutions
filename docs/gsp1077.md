# GSP1077 - Google Kubernetes Engine Pipeline using Cloud Build

Pipeline CI/CD dua repo GitHub: `hello-cloudbuild-app` (kode) dan
`hello-cloudbuild-env` (manifest Kubernetes). Push ke app → Cloud Build test,
build image, dorong manifest baru ke branch `candidate` repo env → trigger
kedua apply manifest ke cluster GKE lalu salin ke branch `production`.

Kelima checkpoint bisa dicapai lewat script, **tapi dua langkah otentikasi
tidak punya API dan wajib dikerjakan sendiri**:

1. `gh auth login` — OAuth device flow di browser.
2. Install **Google Cloud Build** GitHub App ke kedua repo — lewat console.
   Tanpa ini `gcloud builds triggers create github` menolak dengan
   `Repository mapping does not exist`.

Karena itu script dipecah tiga fase, dengan langkah manual di antara `setup`
dan `ci`.

## Jalankan

```bash
curl -sLO https://raw.githubusercontent.com/ravi-arnan/gsp_lab_solutions/main/gsp1077.sh

REGION=us-east4 bash gsp1077.sh setup     # Task 1-3, ~10 menit (cluster GKE)
#   -> pasang Cloud Build GitHub App ke KEDUA repo (instruksinya dicetak script)
REGION=us-east4 bash gsp1077.sh ci        # Task 4
REGION=us-east4 bash gsp1077.sh deliver   # Task 5-6
```

Jangan di-pipe ke `bash`: script butuh argumen fase dan filenya masih dipakai
fase berikutnya.

Kalau `gh auth login` belum pernah dijalankan, fase `setup` berhenti di awal
dan mencetak perintahnya. Pilih **GitHub.com → HTTPS → Yes (authenticate Git)
→ Login with a web browser**.

### Langkah manual di tengah

Setelah fase `setup` selesai, di console:

1. Cloud Build → **Triggers** → region `us-east4` → **Create Trigger**
2. Source → **Connect new repository** → GitHub (Cloud Build GitHub App) → Continue
3. Login GitHub. Kalau muncul *"The GitHub App is not installed"*: klik
   **Install Google Cloud Build**, pilih **Only select repositories**, centang
   **kedua** repo (`hello-cloudbuild-app` dan `hello-cloudbuild-env`), Install.
4. Centang *"I understand that GitHub content..."* → **Connect**.
5. **Tutup form Create Trigger** — triggernya dibuat script, bukan lewat UI.

Kedua repo harus dicentang sekarang. Kalau cuma app yang dipasang, fase
`deliver` gagal saat membuat trigger kedua.

## Task

| Checkpoint | Fase | Catatan |
|-----------|------|---------|
| 1. Enable services, artifact registry, GKE cluster | setup | cluster dibuat `--async`, ditunggu di akhir fase |
| 2. Create the container image with Cloud Build | setup | `gcloud builds submit --tag` dari commit lokal pertama |
| 3. Create the Continuous Integration (CI) Pipeline | ci | trigger `hello-cloudbuild`, branch `.*` |
| 4. Accessing GitHub from a build via SSH keys | deliver | ssh-keygen → Secret Manager + deploy key repo env |
| 5. Create the Test Environment and CD Pipeline | deliver | trigger `hello-cloudbuild-deploy`, branch `^candidate$` |
| 7-8. Cek aplikasi, ubah teks | manual | tidak di-score, perintahnya dicetak di akhir |
| 9. Rollback | manual | Build History repo env → build kedua terbaru → **Rebuild** |

## Catatan

- **Deploy key dipasang lewat CLI**, bukan UI seperti teks lab:
  `gh repo deploy-key add id_github.pub -R <user>/hello-cloudbuild-env -t SSH_KEY -w`.
  Private key-nya masuk Secret Manager lewat
  `gcloud secrets create ssh_key_secret --data-file=`, bukan upload manual.
  `cloudbuild.yaml` menunjuk `versions/1`, jadi kalau secret dibuat ulang
  script menghapus dulu supaya versinya kembali 1.
- **Kunci harus sepasang.** Kalau salah satu sisi hilang (secret ada tapi deploy
  key tidak, atau sebaliknya), script membuang keduanya dan generate ulang.
  Kunci lama yang tidak cocok bikin `git clone` di dalam build gagal dengan
  `Permission denied (publickey)` — dan itu baru kelihatan di log build.
- **Trigger CD dibuat setelah branch `candidate` di-push**, bukan sebelum.
  Kalau urutannya dibalik, push branch pertama menjalankan build padahal
  `kubernetes.yaml` belum ada — build merah tanpa sebab yang jelas. Urutan ini
  sama dengan teks lab, dan memang penting.
- **`container.developer` diberikan ke dua service account.** Teks lab cuma
  memberi ke `<num>@cloudbuild.gserviceaccount.com`, padahal triggernya
  dikonfigurasi memakai Compute Engine default SA — SA itu yang benar-benar
  menjalankan `kubectl apply`. Diberikan ke keduanya supaya tidak tergantung
  mana yang dipakai.
- **`options: logging: CLOUD_LOGGING_ONLY` wajib** untuk build yang memakai
  service account non-default. `cloudbuild.yaml` bawaan bucket belum tentu
  punya blok itu, jadi `fetch_sample()` menambahkannya kalau belum ada.
- **Region di-sed dari `us-central1`**, mengikuti teks lab, pada
  `cloudbuild.yaml`, `cloudbuild-delivery.yaml`, `cloudbuild-trigger-cd.yaml`,
  dan `kubernetes.yaml.tpl`.
- `cloudbuild.yaml` versi CD di script ditulis ulang, bukan menyalin
  `cloudbuild-delivery.yaml` dari bucket — file bawaan itu masih menunjuk Cloud
  Source Repositories, sedangkan lab versi sekarang memakai GitHub lewat SSH.
- Langkah `sed ... | git fetch origin production` di teks lab dibiarkan hilang:
  output `sed`-nya tidak dipakai siapa pun (`git fetch` mengabaikan stdin), itu
  sisa dari versi lama. Manifest yang dipakai adalah yang sudah di-apply,
  diambil dengan `git checkout $COMMIT_SHA kubernetes.yaml`.

### Jebakan langkah manual yang terkonfirmasi

Kalau GitHub App **sudah pernah** dipasang di akunmu dari lab lain, dropdown
repository cuma memperlihatkan repo pilihan lama dan kedua repo lab tidak ada
di situ. Klik **Edit repositories on GitHub** di dasar dropdown, tambahkan
keduanya, Save, lalu tutup dan buka lagi panel Connect repository — daftarnya
di-cache.

**Region di form Create Trigger harus diganti ke region lab sebelum menekan
Connect new repository.** Defaultnya `global`, dan koneksi repository tercatat
per-region; kalau salah, `triggers create` gagal dengan `Repository mapping
does not exist`. Panel Connect repository menampilkan regionnya di pojok kiri
atas, gampang diperiksa.

Selesai connect, toast **"Connected 2 repositories"** muncul. Itu tandanya
cukup — form Create Trigger-nya di-**Cancel**, jangan diisi.
