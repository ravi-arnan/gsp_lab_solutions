# GSP395 - Create and Manage AlloyDB Instances: Challenge Lab

Runbook untuk [`gsp395.sh`](../gsp395.sh). Status: **terverifikasi 100/100** (2026-08-10, region `us-west1`), semua checkpoint hijau.

## Cara jalan

```bash
curl -sLO https://raw.githubusercontent.com/ravi-arnan/gsp_lab_solutions/main/gsp395.sh
REGION=<region dari panel lab> bash gsp395.sh
```

Dua pertanyaan di awal: region dan network. Panel lab sering menampilkan **zone** (`us-west1-c`) sementara AlloyDB minta **region** — script memotong sufiks zone-nya sendiri, jadi dua-duanya diterima. **Region wajib cocok dengan panel lab** — private services access hanya disiapkan di sana, dan cluster di region lain tidak akan bisa dijangkau VM client. Network defaultnya `peering-network`.

| Task | Otomatis | Cara |
|------|----------|------|
| 1 Cluster + instance PRIMARY | ya | `gcloud beta alloydb clusters create` + `instances create --instance-type=PRIMARY --cpu-count=2` |
| 2 Tabel | ya | psql lewat SSH ke `alloydb-client` |
| 3 Data | ya | idem, satu sesi psql yang sama |
| 4 Read pool | ya | `--instance-type=READ_POOL --read-pool-node-count=2` |
| 5 Backup | ya | `gcloud beta alloydb backups create lab-backup` |

Lama ~20 menit, hampir semuanya menunggu AlloyDB.

## Kenapa SQL-nya dijalankan lewat SSH

AlloyDB hanya punya private IP di VPC `peering-network`. Cloud Shell tidak ada di VPC itu, jadi `psql -h <private-ip>` dari Cloud Shell **tidak akan pernah connect**. Script mengirim satu script remote lewat `gcloud compute scp` lalu menjalankannya via SSH di VM `alloydb-client` — pola yang sama dengan `gsp038.sh` dan `arc132.sh`.

Dua detail di script remote itu:

- **`psql -v ON_ERROR_STOP=1` wajib.** Tanpa itu psql tetap keluar dengan status 0 walau DDL-nya gagal, dan script melapor SELESAI padahal tabelnya tidak pernah jadi.
- **`DROP TABLE IF EXISTS ... CASCADE` di depan.** Membuat langkah ini idempoten: rerun tidak menabrak `CREATE TABLE` yang sudah ada dan tidak menggandakan baris data.

`~/alloydbip.txt` tetap ditulis di VM sesuai instruksi lab, walaupun script sendiri tidak membutuhkannya.

## Read pool dibuat di latar belakang

Read pool (~5 menit) tidak bergantung pada isi tabel, jadi script memulainya dengan `&` lalu mengerjakan Task 2 dan 3 sambil menunggu, dan `wait` sebelum Task 5. Menghemat sekitar 5 menit.

Backup **tidak** ikut diparalelkan: cluster AlloyDB menolak operasi baru selagi ada operasi lain berjalan, jadi Task 5 baru mulai setelah read pool benar-benar selesai.

Kalau pembuatan read pool gagal, log-nya (`/tmp/gsp395-readpool.log`) dicetak dan script berhenti — kegagalan di background tidak boleh lewat diam-diam.

## Idempoten

Aman diulang. Cluster, instance, read pool, dan backup dilewati kalau sudah ada; tabel dibuat ulang dari nol setiap kali.
