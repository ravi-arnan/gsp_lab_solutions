# GSP526 - Privileged Access with IAM: Challenge Lab

Runbook untuk [`gsp526.sh`](../gsp526.sh). Status: **belum diuji di lab sungguhan**.

Lab ini soal Privileged Access Manager (PAM). Seluruhnya bisa lewat `gcloud pam` (sudah GA), tapi **dua fase harus dijalankan sebagai user kedua** — itu bukan keterbatasan script, melainkan inti labnya.

## Urutan

```bash
curl -sLO https://raw.githubusercontent.com/ravi-arnan/gsp_lab_solutions/main/gsp526.sh
bash gsp526.sh                       # Task 1, 2, 3 + permintaan grant
# klik checkpoint Task 1, 2, 3

gcloud auth login                    # login sebagai user 2 (Cymbal Security Lead)
bash gsp526.sh approve               # Task 4
# klik checkpoint Task 4 — TUNGGU 1-2 menit dulu, log approval telat muncul
bash gsp526.sh revoke                # Task 5
# klik checkpoint Task 5

gcloud config set account <email user 1>
bash gsp526.sh delete                # Task 6
```

Alternatif untuk fase approve/revoke: kerjakan lewat Console di jendela incognito seperti instruksi lab. Hasilnya sama; `gcloud auth login` di Cloud Shell cuma lebih cepat.

## Kenapa approve tidak bisa dijalankan user pertama

PAM hanya menerima persetujuan dari principal yang terdaftar di `approvalWorkflow.manualApprovals.steps[].approvers`. Owner project sekalipun ditolak kalau bukan approver. Task 2 menetapkan approver = user kedua, dan checkpoint Task 2 memeriksa itu, jadi tidak ada jalan memutar.

## Service agent PAM memakai nomor ORGANISASI

Jebakan terbesar Task 1. Kebanyakan service agent berbentuk `service-<PROJECT_NUMBER>@...`, tapi PAM **selalu** memakai agent tingkat organisasi, bahkan ketika PAM dipakai di tingkat project:

```
service-org-<ORGANIZATION_NUMBER>@gcp-sa-pam.iam.gserviceaccount.com
```

Script mengambil nomor organisasi lewat `gcloud projects get-ancestors`, lalu memberikan `roles/privilegedaccessmanager.serviceAgent` di tingkat project. Service agent baru muncul beberapa saat setelah API diaktifkan, jadi binding-nya dicoba ulang sampai lima kali dengan jeda 15 detik.

## Isi entitlement

| Parameter lab | YAML |
|---------------|------|
| Entitlement Name `pam-entitlement` | argumen posisional |
| Role Compute Admin | `roleBindings[].role: roles/compute.admin` |
| Maximum duration 10 jam | `maxRequestDuration: 36000s` |
| Requester principal (user 1) | `eligibleUsers[].principals` |
| Justification **Not required** | `requesterJustificationConfig: notMandatory: {}` |
| Approver principal (user 2) | `approvalWorkflow.manualApprovals.steps[].approvers[].principals` |
| Number of approvers 1 | `approvalsNeeded: 1` |

Task 3 menulis ulang file yang sama dengan `maxRequestDuration: 14400s` lalu `entitlements update`. `update` tidak butuh update mask — file YAML-nya adalah konfigurasi baru yang utuh, jadi seluruh isi harus tetap lengkap, bukan cuma field yang berubah.

**File update wajib memuat `etag` terkini**, kalau tidak gcloud menolak dengan `ABORTED: The entitlement was modified before this operation`. Ini pasti terjadi kalau update menyusul create, karena create baru saja mengubah etag-nya. Script mengambil etag lewat `describe` tepat sebelum update dan mengulang sampai tiga kali kalau masih basi. `update` juga bertanya konfirmasi, jadi butuh `-q`.

Perhatikan `notMandatory: {}`, bukan `unstructured: {}`. Yang kedua berarti justification **wajib**, kebalikan dari yang diminta lab.

## Deteksi otomatis

| Nilai | Sumber |
|-------|--------|
| Requester (user 1) | akun gcloud aktif |
| Approver (user 2) | principal `user:` di IAM policy project yang bukan akun aktif |
| Nomor organisasi | `gcloud projects get-ancestors` |
| Grant yang disetujui / dicabut | `gcloud pam grants search --caller-relationship=can-approve` / `had-approved` |

`grants search` dengan `can-approve` cuma mengembalikan grant yang memang boleh disetujui akun aktif, jadi sekaligus jadi pemeriksaan bahwa login user kedua sudah benar. Kalau kosong, script berhenti dengan pesan yang tepat alih-alih mencoba approve dan gagal.

## Troubleshooting

| Gejala | Sebab dan solusi |
|--------|------------------|
| `Tidak ada grant yang bisa di-approve` | Masih login sebagai user pertama. Jalankan `gcloud auth login` sebagai user kedua. |
| Gagal memberi role ke service agent setelah 5 percobaan | API baru diaktifkan. Tunggu semenit, jalankan ulang fase setup (idempoten). |
| Checkpoint Task 4 merah padahal approve sukses | Log approval memang telat 1-2 menit. Tunggu, klik lagi. |
| `PERMISSION_DENIED` saat approve | Akun aktif bukan approver principal di entitlement. |
| `Organization tidak terdeteksi` | Project tidak punya ancestor organisasi. Cek `gcloud projects get-ancestors <PROJECT>`. |
| `ABORTED: The entitlement was modified before this operation` | etag basi. Script sudah mengulang otomatis; kalau tetap gagal, jalankan ulang fase setup. |
| Checkpoint Task 3 merah | `maxRequestDuration` masih 36000s. Fase setup selalu menulis ulang jadi 14400s, jalankan ulang. |
