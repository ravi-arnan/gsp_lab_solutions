# GSP528 - Connecting Cloud Networks with NCC: Challenge Lab

Runbook untuk [`gsp528.sh`](../gsp528.sh). Status: **terverifikasi 100/100** (2026-08-07). Nama resource lab tidak dihardcode — script mendeteksi sendiri VPC dan VPN tunnel yang ada.

Nama yang muncul di lab yang diuji: `on-prem-office-1-vpc`, `on-prem-office-2-vpc`, `routing-vpc`, `workload-vpc-1`, `workload-vpc-2`. Deteksi otomatis kena semuanya, tinggal Enter lima kali.

## Peringatan utama: dua fase, urutannya wajib

Satu VPC network hanya boleh menempel ke **satu hub** (`A VPC spoke can be connected to one hub at a time`, [dokumentasi NCC](https://docs.cloud.google.com/network-connectivity/docs/network-connectivity-center/concepts/vpc-spokes-overview)). Workload VPC 1 dipakai dua kali oleh lab:

- Task 2 — spoke bernama `workload-1-spoke` di hub Task 2
- Task 3 — spoke bernama `hybrid-workload-1-spoke` di hub Task 3

Keduanya tidak bisa hidup bersamaan. Jadi:

```bash
curl -sLO https://raw.githubusercontent.com/ravi-arnan/gsp_lab_solutions/main/gsp528.sh
bash gsp528.sh            # Task 1 + Task 2
# klik Check my progress Task 1 dan Task 2 — TUNGGU sampai keduanya HIJAU
bash gsp528.sh task3      # Task 3 (melepas spoke workload-1 lalu bikin hub hybrid)
```

Nilai checkpoint yang sudah hijau tidak dicabut lagi. Kalau `task3` dijalankan sebelum Task 2 hijau, poin Task 2 hilang dan harus dibangun ulang.

Bonus kecil: spoke Task 3 sengaja dinamai `hybrid-workload-1-spoke` — mengandung `workload-1` **dan** `hybrid`, jadi kalau grader Task 2 dijalankan ulang setelah Task 3 masih ada peluang tetap hijau. Jangan diandalkan.

## Yang dibuat

| Task | Hub | Spoke | Tipe |
|------|-----|-------|------|
| 1 | `ncc-hub-onprem` | `office-1-spoke`, `office-2-spoke` | VPN tunnel (hybrid), `--site-to-site-data-transfer` |
| 2 | `ncc-hub-workload` | `workload-1-spoke`, `workload-2-spoke` | VPC network |
| 3 | `ncc-hub-hybrid` | `hybrid-office-1-spoke`, `hybrid-workload-1-spoke` | VPC network |

`--site-to-site-data-transfer` di Task 1 bukan opsional. Tanpa itu trafik on-prem ke on-prem tidak dirutekan lewat hub dan uji ping gagal walaupun spoke-nya ACTIVE.

## Deteksi resource

Script tidak menghardcode nama apa pun. Urutannya:

1. `gcloud compute networks list` → cocokkan pola untuk On-Prem Office 1/2, Workload 1/2, dan VPC routing.
2. `gcloud compute vpn-gateways list` → bangun peta `gateway → VPC`.
3. `gcloud compute vpn-tunnels list` → ambil tunnel yang `vpnGateway`-nya ada di VPC routing, lalu tentukan tunnel itu menuju kantor mana lewat `peerGcpGateway`. Ini lebih akurat daripada menebak dari nama.
4. Kalau peer gateway kosong (classic VPN), baru jatuh ke pencocokan nama tunnel.

**Jangan pakai `network` pada `vpn-tunnels`.** Resource VpnTunnel tidak punya field itu (yang punya VPN gateway), jadi `--format='...network.basename()'` menghasilkan string kosong tanpa error dan semua filter jadi diam-diam gagal. Ini bug versi pertama script, terbukti di lab.

Setiap tebakan dicetak dan ditanyakan ulang lewat helper `ask`, jadi bisa dikoreksi saat itu juga.

## Kalau deteksi meleset

Tekan Ctrl-C, lihat daftar VPC yang dicetak, lalu ulangi dengan env var:

```bash
ONPREM1=on-prem-office-1 ONPREM2=on-prem-office-2 \
WL1=workload-vpc-1 WL2=workload-vpc-2 ROUTING=routing-vpc \
bash gsp528.sh
```

Env var menang atas jawaban interaktif dan atas default.

## Uji konektivitas

Lab meminta "test the connectivity". Script melakukannya best-effort: ambil satu VM per VPC, lalu `gcloud compute ssh --tunnel-through-iap` + `ping -c 3` ke IP internal VM lawan. Gagal di sini **tidak** menggagalkan script — firewall SSH atau ketiadaan IAP bukan bagian yang dinilai. Matikan dengan `TEST=0`.

Kalau mau uji manual di Console: SSH ke VM di On-Prem Office 1, `ping <internal IP VM On-Prem Office 2>`.

## Troubleshooting

| Gejala | Sebab dan solusi |
|--------|------------------|
| `VPN tunnel tidak terdeteksi` | Script mencetak daftar tunnel mentah + peta gateway sebelum keluar. Isi manual: `TUN_OFFICE1=t1,t2 TUN_REGION1=us-east1 TUN_OFFICE2=t3,t4 TUN_REGION2=us-east1 bash gsp528.sh`. |
| Spoke VPN lama ACTIVE | Normal, butuh 1-3 menit. gcloud menunggu sendiri. |
| `RESOURCE_IN_USE` saat bikin spoke Task 3 | Workload VPC 1 masih nempel di hub Task 2 dan penghapusan belum kelar. Ulangi `bash gsp528.sh task3` (idempoten). |
| Checkpoint Task 1 merah padahal spoke ACTIVE | Cek spoke dibuat dengan `--site-to-site-data-transfer`. Kalau tidak, hapus spoke lalu jalankan ulang. |
| Ping antar VM gagal | Firewall di VPC tujuan belum mengizinkan ICMP dari range VPC sumber. Bukan urusan NCC; checkpoint tetap bisa hijau. |
| Overlap subnet saat bikin VPC spoke | Dua VPC spoke di satu hub tidak boleh punya range bertabrakan. Kalau muncul, berarti VPC yang terdeteksi salah. |
