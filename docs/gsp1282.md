## Urutan yang tidak boleh ditukar

Lab ini sengaja dibuat berurutan, dan script mengikutinya:

1. Discovery config dibuat **PAUSED** dulu. Kalau langsung `RUNNING`, scan berjalan sebelum service agent punya izin tagging, dan tidak ada resource yang ditandai.
2. Service agent DLP (`service-<PROJECT_NUMBER>@dlp-api.iam.gserviceaccount.com`) baru ada setelah DLP API dipakai. Karena itu grant `roles/resourcemanager.tagUser` dilakukan **setelah** discovery config dibuat, bukan sebelum.
3. Baru setelah tag key dan izin siap, config di-`PATCH` untuk menambah action `tagResources` sekaligus mengubah status jadi `RUNNING`.

## Empat detail API yang gampang salah

1. **`updateMask` mengganti seluruh field, bukan menambah.** `PATCH ...?updateMask=actions,status` harus mengirim ulang `exportData` dan `publishToScc`, kalau tidak keduanya hilang dan checkpoint Task 1 bisa ikut merah.
2. **Target BigQuery pakai `otherTables`, bukan `others`.** Cloud Storage pakai `filter.others`, BigQuery pakai `filter.otherTables`. Salah satu huruf, config ditolak.
3. **Skor sensitivitas "unknown" itu `SENSITIVITY_UNKNOWN`,** bukan `SENSITIVITY_SCORE_UNSPECIFIED`. Yang terakhir itu nilai "tidak dipakai" dan tidak akan pernah cocok dengan profil apa pun.
4. **Kondisi IAM harus lewat file.** `gcloud ... --condition=` memecah argumennya pakai koma, sedangkan `resource.matchTag('proj/sensitivity-level', 'low')` mengandung koma dan langsung ditolak. Script menulis kondisinya ke file sementara lalu pakai `--condition-from-file`.

## Yang juga perlu dicabut

Checkpoint conditional access tidak cukup dengan menambah binding bersyarat. Binding `roles/viewer` dan `roles/bigquery.dataViewer` **tanpa** kondisi harus dicabut dulu — kalau tidak, Username 2 tetap melihat semua dataset dan kondisinya tidak berefek. Script mencabut keduanya sebelum menambahkan yang bersyarat.

## Checkpoint Task 4 menolak konfigurasi yang benar (belum terpecahkan)

Diuji 2026-07-31: empat checkpoint pertama hijau (80/100), **Explore conditional access for BigQuery using tags tetap 0/20** dengan pesan grader *"Please grant conditional access to resources based on the value of the sensitivity level tag."*

Yang sudah diverifikasi ada dan benar waktu itu:

- Binding `roles/bigquery.dataViewer` untuk Username 2 dengan kondisi berjudul `Low Sensitivity Data Access Only`
- `roles/viewer` sudah tercabut, `roles/browser` ada, tidak ada `dataViewer` tanpa kondisi
- Tag binding `sensitivity-level/low` menempel di `damaged_car_image_info`, lokasi cocok (`us-central1`)
- Metadata dataset juga benar: `bq show` menunjukkan `resourceTags: {"PROJECT/sensitivity-level": "low"}`, jadi binding lewat `gcloud` **sama saja** dengan lewat BigQuery > Edit details > Tags
- **Terbukti berfungsi**: login sebagai Username 2, hanya `damaged_car_image_info` yang muncul di BigQuery

Empat variasi kondisi sudah dicoba, semuanya ditolak:

| Variasi | Hasil |
|---------|-------|
| `resource.matchTag('PROJECT/sensitivity-level', 'low')` — kutip tunggal, output `gcloud` | 0/20 |
| `resource.matchTag("PROJECT/sensitivity-level", "low")` — kutip ganda, **bentuk yang ditulis Console sendiri** lewat condition builder | 0/20 |
| `resource.matchTagId('tagKeys/NNN', 'tagValues/NNN')` | 0/20 |
| Sama seperti baris kedua, tapi field `description` dibuang sehingga kondisinya cuma `title` + `expression` | 0/20 |

Variasi kedua dihasilkan dengan mengerjakan Task 4 murni lewat Console persis seperti langkah lab, jadi ini bukan soal script. Kesimpulan: grader memeriksa sesuatu di luar apa yang tertulis di instruksi lab, atau lagi rusak. Kalau kamu menemukan penyebabnya, catat di sini.

**Run kedua (2026-07-31, project `qwiklabs-gcp-02-8eac3c51665b`): hasil sama, 80/100.** Kali ini verifikasi fungsionalnya tuntas — login sebagai Username 2 setelah propagasi penuh, Explorer benar-benar cuma menyisakan `damaged_car_image_info`, dan `bq_discovery` membalas `Permission bigquery.datasets.get denied`. Jadi kondisinya bekerja persis seperti yang lab gambarkan, tapi checkpoint tetap 0/20 dengan pesan yang sama. Menunggu 5-10 menit lalu klik ulang juga tidak mengubah apa pun.

Yang **tidak** perlu diuji ulang, sudah terbukti bukan penyebabnya: bentuk kutip ekspresi, `matchTag` vs `matchTagId`, ada tidaknya `description`, jalur pemasangan tag (`gcloud` vs BigQuery UI), lokasi tag binding, dan propagasi IAM.

Diagnosisnya jangan diulang dari nol — `bash gsp1282.sh diag` mencetak state keenam bagian (discovery config + `tagConditions`, tag values, role service agent, role Username 2 + kondisi, semua dataset dengan lokasi dan tag binding-nya, jumlah profil hasil scan) tanpa mengubah apa pun.

Catatan lain dari run yang sama: scan menghasilkan 467 profil, tapi `car_buyers` **tidak** ikut ditandai `high` oleh auto-tagging selama durasi lab. Tidak menghalangi checkpoint mana pun, tapi jangan kaget kalau diag 5 menunjukkan hanya satu dataset yang punya tag.

## Troubleshooting

| Gejala | Sebab dan solusi |
|--------|------------------|
| `Service account service-...@dlp-api... does not exist` | DLP API baru saja di-enable, service agent belum dibuat. Tunggu semenit, jalankan ulang script. |
| Discovery config gagal, `Invalid value at 'targets'` | Field target BigQuery salah nama. Lihat poin 2 di atas. |
| Binding tag gagal | Lokasi binding harus sama dengan lokasi dataset. Script membacanya dari `bq show`, default `us-central1` kalau gagal. |
| Username 2 masih melihat semua dataset | Propagasi IAM butuh 5-10 menit. Kalau setelah itu masih, cek apakah `roles/viewer`-nya benar tercabut di halaman IAM. |
| Looker dashboard kosong | Scan baru mulai. Hasil butuh beberapa menit. Di tab Profiles set Location type = Region > us-central1. |
